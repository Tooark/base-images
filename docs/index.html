O job já nasce com as ferramentas

The job starts with its tools in place

Em vez de instalar AWS CLI, kubectl ou OpenTofu a cada execução, o job roda dentro de um container que já tem tudo, na versão certa e sem nada além do necessário.

Instead of installing the AWS CLI, kubectl or OpenTofu on every run, the job runs inside a container that already has them, at the right version and with nothing it does not need.

Cada pasta da raiz do repositório é uma imagem, publicada como ghcr.io/tooark/<imagem>. Elas se dividem por fluxo, mas todas seguem o mesmo contrato:

Each folder at the repository root is one image, published as ghcr.io/tooark/<image>. They split by flow, but all of them follow the same contract:

All of them start from {{BASE_IMAGE}}: an OS package fix reaches every image in the same build.

Every Saturday a workflow looks up each tool's latest stable version and builds whatever changed.

Tags e versões

Tags and versions

Toda release publica a mesma imagem com quatro tags. Qual delas usar depende de quanto você quer que o pipeline mude sozinho.

Every release publishes the same image under four tags. Which one to use depends on how much you want the pipeline to change on its own.

Tag ExemploExample ComportamentoBehaviour
MAJOR.MINOR.PATCH aws-cli:{{aws-cli}} Nunca muda: a build pula versões que já têm release. É a forma de travar uma versão. Never changes: the build skips versions that already have a release. This is how you pin a version.
MAJOR.MINOR aws-cli:{{aws-cli:MINOR}} Recebe os patches. Recomendada para pipelines. Picks up patches. Recommended for pipelines.
MAJOR aws-cli:{{aws-cli:MAJOR}} Acompanha a linha major inteira, minors incluídas. Follows the whole major line, minors included.
latest aws-cli:latest A última release, mesmo com quebra de compatibilidade. Bom para testar na máquina, ruim para CI. The latest release, breaking changes included. Fine on your machine, poor for CI.

De onde vem o número da versão

Where the version number comes from

Imagens de uma ferramenta só usam a versão dela: aws-cli:{{aws-cli}} traz o AWS CLI {{aws-cli}}, e o mesmo vale para gcloud-cli, tofu e sonar-scanner. As imagens compostas (dockerx, tofu-aws, tofu-gcloud, tofu-aws-gcloud e security-scanner) têm um contador próprio, que sobe no mesmo nível — major, minor ou patch — da maior mudança entre as ferramentas principais dela. Por isso tofu-gcloud:{{tofu-gcloud}} traz OpenTofu {{tofu-gcloud:OPENTOFU_VERSION}}, e não OpenTofu {{tofu-gcloud}}.

Single-tool images use that tool's version: aws-cli:{{aws-cli}} ships AWS CLI {{aws-cli}}, and the same goes for gcloud-cli, tofu and sonar-scanner. Composite images (dockerx, tofu-aws, tofu-gcloud, tofu-aws-gcloud and security-scanner) carry their own counter, which moves at the same level — major, minor or patch — as the largest change among their main tools. That is why tofu-gcloud:{{tofu-gcloud}} ships OpenTofu {{tofu-gcloud:OPENTOFU_VERSION}}, not OpenTofu {{tofu-gcloud}}.

Como as imagens rodam

How the images run

Todas as imagens usam o mesmo docker-entrypoint.sh. Entender o que ele faz explica por que a mesma imagem se comporta diferente no docker run, no GitHub Actions e no GitLab CI.

Every image uses the same docker-entrypoint.sh. Knowing what it does explains why the same image behaves differently under docker run, GitHub Actions and GitLab CI.

  1. Ajusta o docker.sock. Se o container sobe como root e há um socket em /var/run/docker.sock, lê o GID dele e coloca o usuário app num grupo com esse GID. O Docker do host funciona sem chmod 666.
  2. Prefixa um comando fixo, se ARK_ENTRYPOINT_CMD estiver definido. É assim que docker run security-scanner full-scan … vira ark-tools full-scan ….
  3. Troca de usuário para app com gosu e faz exec do comando: sinais e exit code passam direto.
  1. Fixes docker.sock. If the container starts as root and there is a socket at /var/run/docker.sock, it reads the socket's GID and adds the app user to a group with that GID. The host's Docker works without chmod 666.
  2. Prepends a fixed command when ARK_ENTRYPOINT_CMD is set. That is how docker run security-scanner full-scan … becomes ark-tools full-scan ….
  3. Switches user to app with gosu and execs the command: signals and the exit code pass straight through.

O entrypoint dentro do CI

The entrypoint inside CI

GitHub Actions

Num job com container:, o runner troca o entrypoint por um processo próprio e roda cada step com docker exec. Os steps rodam como root e com HOME=/github/home; credenciais por variável de ambiente funcionam do mesmo jeito.

In a job with container:, the runner replaces the entrypoint with its own process and runs each step through docker exec. Steps run as root with HOME=/github/home; credentials passed as environment variables work the same.

GitLab CI

O runner mantém o entrypoint da imagem e entrega a ele o shell do job, que roda como app. No security-scanner, que prefixa ark-tools, limpe o entrypoint com entrypoint: [""] e chame ark-tools no script.

The runner keeps the image entrypoint and hands it the job's shell, which runs as app. In security-scanner, which prepends ark-tools, clear the entrypoint with entrypoint: [""] and call ark-tools in script.

No CI: build multi-arquitetura com push

In CI: multi-architecture build and push

O tonistiigi/binfmt registra o emulador de arm64 no host; sem ele, os passos RUN da arquitetura que não é a do runner falham. No GitLab, o docker:dind exige um runner com privileged = true.

tonistiigi/binfmt registers the arm64 emulator on the host; without it, RUN steps for the architecture the runner is not fail. On GitLab, docker:dind needs a runner with privileged = true.

GitHub Actions

name: image

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    container:
      image: ghcr.io/tooark/dockerx:{{dockerx:MINOR}}
    steps:
      - uses: actions/checkout@v7

      - name: Log in to GHCR
        env:
          TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: echo "$TOKEN" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin

      - name: Build and push (amd64 + arm64)
        run: |
          docker run --privileged --rm tonistiigi/binfmt --install arm64
          docker buildx create --name ci --driver docker-container --use --bootstrap
          docker buildx build --platform linux/amd64,linux/arm64 \
            -t ghcr.io/acme/myapp:${{ github.sha }} --push .

GitLab CI

build_image:
  stage: build
  image: ghcr.io/tooark/dockerx:{{dockerx:MINOR}}
  services:
    - docker:dind
  variables:
    DOCKER_HOST: tcp://docker:2375
    DOCKER_TLS_CERTDIR: ""
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
    - docker run --privileged --rm tonistiigi/binfmt --install arm64
    - docker buildx create --name ci --driver docker-container --use --bootstrap
    - docker buildx build --platform linux/amd64,linux/arm64 -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" --push .

No CI

In CI

Deploy em EKS no GitHub e sincronização com S3 no GitLab. No GitLab, cadastre AWS_ACCESS_KEY_ID e AWS_SECRET_ACCESS_KEY como variáveis mascaradas do projeto: o runner já as exporta para o job.

An EKS deploy on GitHub and an S3 sync on GitLab. On GitLab, set AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY as masked project variables: the runner exports them to the job already.

GitHub Actions

name: deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    container:
      image: ghcr.io/tooark/aws-cli:{{aws-cli:MINOR}}
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
      AWS_REGION: us-east-1

      - uses: actions/checkout@v7

      - name: Point kubectl at the EKS cluster
        run: aws eks update-kubeconfig --name "${{ vars.EKS_CLUSTER }}"

      - name: Deploy
        run: |
          kubectl apply -f k8s/
          kubectl rollout status "deployment/${{ vars.APP_NAME }}" --timeout=120s

Verificar a assinatura

Verify the signature

Antes de confiar uma credencial de produção a uma imagem, dá para provar que ela saiu do workflow de build deste repositório, e não de outro lugar.

Before trusting an image with a production credential, you can prove it came out of this repository's build workflow and nowhere else. 

cosign verify ghcr.io/tooark/aws-cli:{{aws-cli}} \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity \
    https://github.com/Tooark/base-images/.github/workflows/image-build.yml@refs/heads/main

A assinatura é keyless: não existe chave privada guardada em lugar nenhum. Na build, o GitHub Actions emite um token OIDC que identifica o workflow, o Sigstore troca esse token por um certificado de vida curta e o registro da assinatura fica no log público de transparência. A verificação confere duas coisas:

The signature is keyless: no private key is stored anywhere. During the build, GitHub Actions issues an OIDC token that identifies the workflow, Sigstore exchanges it for a short-lived certificate, and the signature record lands in the public transparency log. Verification checks two things:

  • --certificate-identity: o certificado foi emitido para o image-build.yml deste repositório, rodando na main.
  • --certificate-oidc-issuer: quem atestou essa identidade foi o GitHub Actions.
  • --certificate-identity: the certificate was issued to this repository's image-build.yml, running on main.
  • --certificate-oidc-issuer: the identity was vouched for by GitHub Actions.

A assinatura é feita sobre o digest do índice multi-arquitetura com --recursive, então qualquer tag de qualquer imagem e as duas arquiteturas verificam com o mesmo comando. Para travar de vez, use o digest que o cosign verify imprime no lugar da tag.

The signature is made over the digest of the multi-arch index with --recursive, so any tag of any image and both architectures verify with the same command. To pin for good, use the digest cosign verify prints instead of the tag.
